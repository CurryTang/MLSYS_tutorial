# 操作系统 3 · 进程间通信与调度

进程之间要协作，绕不开两个基础问题：数据怎么从一个进程传到另一个进程，以及操作系统怎么决定"现在该轮到谁用 CPU"。这一讲先把六种经典的进程间通信（IPC）方式逐一讲清楚——管道、命名管道、消息队列、信号量、共享内存、socket——重点辨析它们各自的数据形式、生命周期和适用场景；再讲进程/线程上下文切换为什么开销不同，这是"多线程比多进程轻量"这句话背后真正的机制；接着过一遍经典调度算法（FCFS、SJF、时间片轮转、多级反馈队列）以及 Linux 现代默认调度器 CFS 的定位；最后把阻塞/非阻塞、同步/异步这两个经常被混为一谈、实际上完全正交的维度分开讲清楚。IO 模型的完整分类（select/poll/epoll 这些具体机制）留到网络编程那一讲详细展开，这里只建立概念框架。

```text
1. 遇到"IPC 方式怎么选"类问题，先问三个问题：需不需要跨主机、需不需要保留消息边界/按类型接收、数据量大不大对延迟敏不敏感。跨主机只能用 socket；需要消息边界和分类接收用消息队列；追求极致延迟且能自己处理同步用共享内存；父子进程间传简单字节流用管道；无亲缘关系但同机器用命名管道或 socket。
2. 遇到"为什么进程切换比线程切换慢"，答案的核心永远是页表切换导致的 TLB flush，而不是笼统地说"进程切换要保存更多东西"。先讲通用的上下文切换流程（保存寄存器/PC → 选下一个任务 → 恢复寄存器/PC → 跳转），再讲进程切换比线程切换多出来的那一步：切 CR3、地址空间变了、TLB 里缓存的旧映射全部作废。
3. 遇到调度算法题，先分清"这个算法解决的核心矛盾是什么"：FCFS 解决"要不要排队"但引入护航效应；SJF 解决"怎么让平均等待最短"但要求预知任务长度；RR 解决"公平和响应性"但要调时间片；MLFQ 解决"既要响应快又要吞吐高"，用多级队列 + 动态降级实现。
4. 遇到"阻塞/非阻塞"和"同步/异步"混着问的题，第一反应是把它们摆成两个独立维度：阻塞/非阻塞问的是"这一次系统调用会不会卡住等数据"，同步/异步问的是"整个IO操作完成之后，是调用方自己去发现的，还是操作系统主动通知的"。先分开定义，再讨论组合，不要试图把两者揉成一个连续谱系。
```

## 1. 进程间通信方式总览

**核心结论**：进程之间默认无法直接访问彼此的内存（每个进程有独立的虚拟地址空间），所有 IPC 机制本质上都是在"绕开这层隔离、借助内核或者约定好的共享资源完成数据传递或同步"。六种经典方式在数据形式、生命周期、是否需要亲缘关系、是否支持跨主机上有明显区别，选型时应该先想清楚这几个维度，而不是死记哪种方式"更快更好"。

**管道（PIPE）**：内核维护的一段**有限大小的字节流缓冲区**（Linux 下默认容量通常是 64KB，可以用 `fcntl(fd, F_SETPIPE_SZ, ...)` 调整），通过 `pipe()` 系统调用创建，一次调用返回一对文件描述符（`fd[0]` 读端、`fd[1]` 写端）。管道本身没有名字，只能在**有亲缘关系的进程之间**使用——典型做法是先 `pipe()` 再 `fork()`，子进程继承父进程的文件描述符表，父子双方各自关闭用不到的一端后就能单向通信。管道里的数据**没有消息边界**，读端看到的只是一串连续字节，不知道对方一次 `write()` 写了多少字节、写了几次，如果需要区分消息边界，应用层必须自己约定分隔符或者长度前缀。

```c
int fd[2];
pipe(fd); // fd[0] 读端，fd[1] 写端
pid_t pid = fork();
if (pid == 0) {
    close(fd[1]);
    char buf[128];
    read(fd[0], buf, sizeof(buf)); // 从父进程读到的只是字节流，没有消息边界
} else {
    close(fd[0]);
    write(fd[1], "hello", 5);
}
```

**命名管道（FIFO）**：底层机制和管道完全一样（内核里同样是一段有限大小的字节流缓冲区），区别在于它以文件系统里的一个**特殊文件**形式存在（用 `mkfifo()` 创建，文件类型是 `p`），因此**没有亲缘关系限制**——任意两个知道这个路径的进程都可以各自 `open()` 它来读写，不需要通过 `fork()` 建立关系。除此之外，FIFO 依然是纯字节流，没有消息边界。

```c
mkfifo("/tmp/myfifo", 0666); // 在文件系统里创建一个特殊文件
// 进程 A（不需要和写端进程有任何亲缘关系，只需要知道路径）
int fd = open("/tmp/myfifo", O_RDONLY);
```

**消息队列（message queue）**：内核维护的一系列**有明确边界的消息节点**，每条消息除了数据本身还带有一个类型（`mtype`）字段，接收方可以指定只接收某个类型的消息，也可以按优先级顺序接收，不像管道那样只能按写入顺序读取整条字节流。消息队列的**生命周期独立于创建它的进程**——进程退出并不会自动销毁消息队列，必须显式调用 `msgctl(msgid, IPC_RMID, ...)` 删除，否则会一直占用内核资源直到系统重启，这是消息队列在实践中容易踩的一个坑。

```c
key_t key = ftok("/tmp", 65);
int msgid = msgget(key, 0666 | IPC_CREAT);

struct msgbuf { long mtype; char mtext[128]; } msg;
msg.mtype = 1; // 消息类型，兼具"分类"和"优先级"的作用
msgsnd(msgid, &msg, sizeof(msg.mtext), 0);

msgrcv(msgid, &msg, sizeof(msg.mtext), 1, 0); // 只接收 mtype == 1 的消息，跳过其他类型
```

**信号量（semaphore）**：本质是一个**内核维护的计数器**，配合原子的 P（`wait`，计数器减一，若已经为 0 则阻塞等待）和 V（`signal`，计数器加一，唤醒等待者）操作使用。信号量**不是用来传输实际数据的通道**，而是用来协调"谁可以进入临界区"或者"某类资源还剩多少个可用"，这一点是它和前面几种 IPC 方式最本质的区别——管道、FIFO、消息队列传的是数据本身，信号量传的是"许可"。

```c
sem_t sem;
sem_init(&sem, 1, 1); // 第二个参数 1 表示可在进程间共享，初始值 1 相当于一把互斥锁
sem_wait(&sem);       // P 操作：计数器减一，若已为 0 则阻塞
// 临界区
sem_post(&sem);       // V 操作：计数器加一，唤醒一个等待者
```

**共享内存（shared memory）**：让多个进程把**同一块物理内存**映射到各自的虚拟地址空间（`shmget`/`shmat`，或者用 `mmap(MAP_SHARED)` 映射同一个文件/匿名对象），映射完成之后各进程读写这块内存**完全不经过内核**——不需要像管道、消息队列那样先把数据拷贝进内核缓冲区再拷贝出来，是速度最快的 IPC 方式。但正因为没有内核介入，共享内存本身**不提供任何同步机制**，多个进程同时读写同一块内存必须自己另外配合信号量、互斥锁之类的机制来协调，否则会出现和多线程共享变量一样的数据竞争问题。

```c
int shmid = shmget(key, 4096, 0666 | IPC_CREAT);
void* addr = shmat(shmid, NULL, 0); // 映射到本进程虚拟地址空间
// 之后直接读写 addr 指向的内存，无系统调用、无内核拷贝
// 但多进程并发访问必须自己用信号量等机制做同步
```

**socket**：既可以用于同一台机器上的进程间通信（Unix domain socket，`AF_UNIX`），也可以跨主机通信（`AF_INET`/`AF_INET6`），是六种方式里**唯一天然支持跨主机**的 IPC 手段，其余方式都局限于同一台机器（共享同一个内核）。socket 涉及的阻塞/非阻塞、以及 `select`/`poll`/`epoll` 这套 IO 多路复用机制内容很多，这里先只把它作为一个 IPC 选项列出，具体的网络编程细节留到后面专门讲网络编程的一讲。

| IPC 方式 | 数据形式 | 是否需要同步机制 | 是否跨主机 |
|---|---|---|---|
| 管道 PIPE | 字节流，无边界 | 内核自动保证读写互斥，无需额外同步 | 否 |
| 命名管道 FIFO | 字节流，无边界 | 同上 | 否 |
| 消息队列 | 离散消息，有边界和类型 | 内核自动保证，无需额外同步 | 否 |
| 信号量 | 不传数据，只是计数器 | 本身就是同步原语 | 否 |
| 共享内存 | 原始内存，无格式约束 | 需要自己配合信号量等机制 | 否 |
| socket | 字节流或数据报，按协议约定 | 内核保证收发原子性，应用层处理并发 | 是（唯一） |

**常见追问 / 面试陷阱**

> 追问"共享内存已经这么快了，为什么还要用消息队列这种要经过内核拷贝的方式"：共享内存快是因为绕过了内核，但代价是同步逻辑完全交给应用层自己处理，一旦同步没做对就是数据竞争甚至内存越界这类难调试的问题；消息队列虽然多了一次内核拷贝的开销，但天然保证了每条消息的完整性和顺序（同一类型内消息不会被拆散或者交叉），还自带按类型选择接收的能力，工程上更省心。选型是"极致性能、自己承担同步复杂度"和"够用的性能、内核帮忙保证正确性"之间的权衡，不是共享内存单方面更优。

## 2. 管道与消息队列对比

**核心结论**：管道和消息队列经常被放在一起比较，因为二者都可以用来在进程间传输"数据"，但底层数据模型完全不同——一个是无结构的字节流，一个是有结构的消息序列。

| 对比维度 | 管道 / 命名管道 | 消息队列 |
|---|---|---|
| 是否有消息边界 | 无，纯字节流，读端不知道对方每次 `write()` 写了多少 | 有，每条 `msgsnd()` 对应一条完整的消息，`msgrcv()` 按条读取 |
| 是否要求进程间亲缘关系 | 管道通常要求（依赖 `fork()` 继承 fd）；命名管道不要求 | 不要求，任意知道 key 的进程都能访问 |
| 是否支持按类型/优先级选择接收 | 不支持，只能按写入顺序读取 | 支持，`msgrcv()` 可以指定只接收特定 `mtype` |
| 生命周期 | 随最后一个持有该 fd 的进程关闭/退出而自动清理 | 独立于进程存在，需要显式 `msgctl(IPC_RMID)` 删除，否则一直占用内核资源 |
| 典型使用场景 | 父子进程间传递简单的连续数据流（比如 shell 里的 `\|`） | 需要区分消息类型、允许乱序到达的进程间任务分发 |

**常见追问 / 面试陷阱**

> 追问"消息队列的生命周期独立于进程会带来什么实际问题"：如果程序异常退出（比如 core dump）却没有走到清理逻辑，消息队列会一直残留在内核里，占用有限的系统资源（`ipcs -q` 可以查看），长期积累可能导致后续 `msgget` 因为达到系统上限而失败。生产环境里常见的做法是启动时先检查、清理遗留的消息队列，或者在设计上避免依赖消息队列的自动清理。

## 3. 进程 / 线程上下文切换的流程与开销对比

**核心结论**：上下文切换的通用流程是固定的四步——保存当前任务的寄存器状态和程序计数器等上下文信息到该任务的内核数据结构里、由调度器选择下一个要运行的任务、恢复该任务此前保存的上下文信息、跳转到恢复出来的位置继续执行。进程切换和线程切换走的都是这四步，但**进程切换必须多做一件事：切换地址空间**，这一步是两者开销差异的根本来源。

**通用流程**：

```text
当前任务运行中
      │  触发切换（时钟中断 / 系统调用阻塞 / 有更高优先级任务就绪）
      ▼
保存当前任务上下文（寄存器、PC、栈指针）→ 存入该任务的内核数据结构
      │
      ▼
调度器选择下一个要运行的任务（按调度算法，如 CFS 选 vruntime 最小者）
      │
      ▼
恢复下一个任务此前保存的上下文（寄存器、PC、栈指针）
      │
      ▼
跳转执行，任务继续运行
```

**为什么进程切换比线程切换更贵**：进程切换除了保存/恢复寄存器上下文之外，还需要**切换页表**——把 CR3 寄存器（x86 架构下指向当前地址空间页表基址的寄存器）更新为指向新进程的页表。这一步的直接后果是 TLB（Translation Lookaside Buffer，缓存"虚拟地址→物理地址"映射的高速缓存）里缓存的旧进程地址映射全部作废：传统实现里 TLB 条目不区分属于哪个进程，一旦 CR3 变了，旧的映射对新进程来说完全无意义，必须整体判定失效，这就是所谓的 **TLB flush**。TLB flush 之后的一段时间里，新进程的内存访问因为 TLB 里没有可用的缓存条目，需要重新走一次完整的页表查询（多级页表遍历）才能建立映射，这个过程比命中 TLB 慢一个数量级以上，会造成切换之后一段时间内内存访问延迟明显升高，直到 TLB 被新进程的常用映射重新"预热"。

线程切换如果发生在**同一进程内**的线程之间，情况完全不同：同一进程的所有线程共享同一套页表（Linux 内核里体现为共享同一个 `mm_struct`），因此线程切换不需要更新 CR3，也就不需要 flush TLB，切换开销基本只剩下保存/恢复寄存器状态和内核栈这部分，明显小于进程切换。这正是"多线程比多进程轻量"这句话背后真正的机制，而不是一个笼统的经验之谈。

```text
线程切换（同进程内）                    进程切换（跨进程）
┌──────────────┐                    ┌──────────────┐
│ 保存寄存器/PC  │                    │ 保存寄存器/PC  │
├──────────────┤                    ├──────────────┤
│ 页表不变        │                    │ 更新 CR3       │
│ 无需 flush TLB │                    │ → TLB flush   │
├──────────────┤                    ├──────────────┤
│ 恢复寄存器/PC  │                    │ 恢复寄存器/PC  │
└──────┬───────┘                    └──────┬───────┘
       ▼                                    ▼
   立即高效访存                    后续访存需重建 TLB，
  （TLB 命中率不受影响）              一段时间内命中率下降
```

**常见追问 / 面试陷阱**

> 追问"现代 CPU 有没有办法缓解进程切换的 TLB flush 开销"：有。现代 x86 处理器支持 **PCID（Process-Context Identifier）**，ARM 上的对应机制是 **ASID（Address Space Identifier）**，其思路是给 TLB 的每条缓存条目额外打上一个进程/地址空间标签，这样切换 CR3 时不再需要把整个 TLB 清空，硬件可以根据标签只使用属于当前进程的那部分缓存条目，其他进程的条目继续保留在 TLB 里，等下次切回去时依然可能命中。这是一个硬件层面的优化，缓解但不能完全消除进程切换比线程切换更贵这个结论——切换地址空间本身仍然比不切换要多做工作，只是"多做多少"因为 PCID/ASID 的存在被显著压低了。

## 4. 进程的调度算法

**核心结论**：调度算法要解决的核心问题是"多个可运行的任务在争抢同一个/同一组 CPU 核心时，先后顺序和每次运行多久该怎么安排"，不同算法本质上是在**平均等待时间、响应时间、吞吐量、公平性、实现复杂度**这几个互相冲突的目标之间做不同的取舍。

**FCFS（First-Come First-Served，先来先服务）**：按任务到达的先后顺序排队执行，谁先来谁先跑完，不抢占。实现最简单，但容易出现**护航效应（convoy effect）**：一个耗时很长的任务排在队首，会让后面一堆本来很快就能跑完的短任务被迫长时间等待，即使这些短任务单独看响应会很快。

**SJF（Shortest Job First，最短作业优先）**：每次都挑当前等待任务里预计执行时间最短的先运行。在任务长度已知的前提下，SJF 在理论上能给出最优的平均等待时间（可以用交换论证证明：把一个更短的任务排到更长任务前面，总能不增加甚至减少平均等待时间）。但它的前提"预知任务长度"在实际系统里很难满足——操作系统通常不知道一个任务接下来还要跑多久，只能靠历史行为做估计，估计不准时 SJF 的优势会打折扣，长任务也可能被不断插队的短任务饿死。

**时间片轮转（Round Robin, RR）**：给每个任务分配一个固定长度的时间片，各任务按顺序轮流执行，用完时间片就被抢占、排到队尾等下一轮。这是抢占式调度，保证了公平性和响应性——任何任务都不会无限期等待。时间片的长度是关键调参：**时间片太长**，RR 退化成近似 FCFS（一个任务可能在一个时间片内就跑完了它想做的所有事，后面的任务照样要等很久）；**时间片太短**，任务频繁被切换，上下文切换的开销占总时间的比例过高，有效计算时间被切换开销侵蚀。

**多级反馈队列（MLFQ, Multi-Level Feedback Queue）**：设置多个优先级队列，队列之间优先级不同（通常优先级越高、单次能获得的时间片越短）。核心规则可以概括为：新到达的任务默认放进最高优先级队列，因此短任务、交互式任务往往刚开始就能获得很快的响应；一个任务如果用满了当前队列分配的时间片却还没执行完，说明它可能是计算密集型的长任务，会被**降级**到下一级优先级更低的队列，用更长的时间片但更低的调度优先级继续执行；如果任务在时间片用完之前就主动让出 CPU（比如等待 IO），则保留在原优先级队列，不会因此被降级。这套机制试图同时兼顾响应时间（短任务、交互任务能快速获得 CPU）和吞吐量（长任务不会被无限期插队打断，也能获得连续执行的机会）。为了避免任务被长期困在低优先级队列里得不到翻身机会（饥饿问题），一些 MLFQ 实现还会周期性地把所有任务重新提升回最高优先级队列（**优先级提升，priority boost**），这样即使一个任务前期表现得像计算密集型，之后行为发生变化（比如从计算阶段转入等待阶段）也有机会重新获得较高优先级。

```text
MLFQ 时间线示意（Q0 优先级最高、时间片最短；Q2 优先级最低、时间片最长）

Q0（时间片=2） │ A ── 用满2个单位仍未完成 → 降级到 Q1
Q1（时间片=4） │         A ── 用满4个单位仍未完成 → 降级到 Q2
Q2（时间片=8） │                   A ── 继续执行 ...

同一时段新任务 B 到达：
Q0（时间片=2） │        B ── 很快执行完，未触发降级，响应迅速
```

| 算法 | 是否抢占 | 是否需要预知任务长度 | 典型问题 |
|---|---|---|---|
| FCFS | 否 | 否 | 护航效应，短任务可能排在长任务后面等很久 |
| SJF | 否（经典版本） | 是 | 长任务可能被持续到达的短任务饿死，长度估计不准会失效 |
| Round Robin | 是 | 否 | 时间片过长退化成 FCFS，过短切换开销占比过高 |
| MLFQ | 是 | 否 | 需要仔细调参数（各级时间片长度、提升周期），实现复杂度更高 |

**CFS（Completely Fair Scheduler）的定位**：Linux 现代默认调度器 CFS 不属于上面这几种经典分类，而是基于**虚拟运行时间（vruntime）**排序：每个可运行任务的 vruntime 按权重换算累加实际占用的 CPU 时间，调度器用一棵红黑树维护所有可运行任务、按 vruntime 排序，每次调度总是挑 vruntime 最小的任务运行，长期来看让每个任务获得的 CPU 时间趋于公平。这部分机制在《性能优化 2·多线程与 CPU 优化》里已经详细展开过（vruntime 的具体计算、红黑树的调度决策、nice 值的作用），这里只从"调度算法分类"的角度指出：CFS 可以看作是对"公平"这个目标做了更精细化处理的方案，不再依赖固定长度的时间片轮转，不重复展开细节。

**常见追问 / 面试陷阱**

> 追问"SJF 和 MLFQ 都想照顾短任务，两者有什么本质区别"：SJF 需要**提前准确知道**任务长度才能排出最优顺序，这个前提在实际系统里很难满足；MLFQ **不需要预知**任务长度，而是通过"观察任务的实际行为"来动态推断——一个任务如果一直用满时间片不肯让出 CPU，系统就把它当作长任务对待并降级，一个任务如果很快执行完或者主动让出，系统就把它当作短/交互式任务对待并保留高优先级。MLFQ 本质上是用运行时的观测和反馈机制去逼近 SJF 试图达到的效果，而不需要 SJF 那个不现实的前提。

## 5. 阻塞 IO 与非阻塞 IO

**核心结论**：阻塞/非阻塞描述的是"发起一次 IO 操作（比如读一个 socket 或者读一个管道）之后，如果数据还没准备好，这一次调用会不会立刻返回"，这是一个**针对单次系统调用**的性质。

**阻塞 IO**：调用线程发起 `read()`/`recv()` 这类调用后，如果数据还没就绪，线程会一直卡在这次系统调用里，进入睡眠状态，直到数据真正就绪并且从内核缓冲区拷贝到用户缓冲区完成才返回。在此期间调用线程完全无法做其他事情，唯一的选择是等待或者用多线程/多进程为每个连接单独分配一个阻塞的执行流。

**非阻塞 IO**：需要显式设置（比如给文件描述符加上 `O_NONBLOCK` 标志）。设置之后，如果调用 `read()`/`recv()` 时数据还没准备好，调用会**立刻返回**，并且返回一个表示"暂时没有数据"的错误码（`EAGAIN` 或者语义等价的 `EWOULDBLOCK`），而不是让调用线程卡住。调用方需要自己决定接下来怎么办——最简单的做法是过一会儿再调用一次，也就是**轮询（polling）**；更高效的做法是配合 `select`/`poll`/`epoll` 这类 IO 多路复用机制一次性监控多个描述符，避免盲目轮询浪费 CPU，这部分内容在网络编程那一讲会详细展开。

```c
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK); // 设置为非阻塞

ssize_t n = read(fd, buf, sizeof(buf));
if (n < 0 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
    // 数据还没准备好，调用立刻返回，而不是卡住
    // 调用方自己决定是否稍后重试
}
```

**常见追问 / 面试陷阱**

> 追问"非阻塞 IO 是不是就等于异步 IO"：不是，这是最常见的混淆点，具体辨析放在下一节展开——非阻塞只是保证"这一次调用不会卡住"，但调用方依然需要自己反复检查/轮询数据是否就绪，这个"等待并检查"的过程本身仍然需要调用方主动参与，属于下一节要讲的"同步"范畴。

## 6. 同步与异步的概念

**核心结论**：同步/异步描述的是和阻塞/非阻塞**正交**的另一个维度——关注点不是"这一次调用会不会卡住"，而是"整个 IO 操作真正完成（数据已经就绪并且拷贝完毕）这件事，是调用方自己主动发现的，还是操作系统主动通知调用方的"。

**同步 IO**：调用方需要自己主动去发起、等待、检查 IO 操作是否完成。不管中间是用阻塞方式死等，还是用非阻塞方式反复轮询，**调用方自己都要参与"等待数据就绪"这个过程**——阻塞方式是调用方的线程被动睡眠等待，非阻塞轮询方式是调用方主动反复发起检查调用，两者本质上都需要调用方自己盯着这件事，区别只在于盯着的方式是"卡住不动"还是"反复探头"。

**异步 IO**：调用方发起一次 IO 请求之后可以**立刻返回去做别的事情**，完全不需要参与"等待数据就绪"这个过程；操作系统会在整个 IO 操作（包括数据从内核搬运到用户缓冲区这一步）真正完成之后，主动通过某种机制（比如回调函数、信号、完成端口/完成队列）通知调用方。调用方从发起请求到收到完成通知之间，理论上不需要做任何和这次 IO 相关的动作。

**2×2 象限**：把"阻塞/非阻塞"和"同步/异步"这两个维度摆在一起，理论上有四种组合：

```text
              │        阻塞           │        非阻塞
──────────────┼───────────────────────┼───────────────────────
    同步        │  传统阻塞 read/recv    │  O_NONBLOCK + 轮询重试
              │  调用方卡在系统调用里    │  调用方反复发起检查，
              │  直到数据就绪并拷贝完   │  自己承担"等待"的过程
──────────────┼───────────────────────┼───────────────────────
    异步        │  理论上极少见，        │  POSIX AIO / Windows IOCP
              │  概念上接近自相矛盾     │  发起后立即返回，OS 完成
              │（"异步"意味着几乎不该卡住）│ 全部工作后主动通知
```

"异步 + 阻塞"这个组合在概念上比较少见：既然异步的定义是"调用方不需要参与等待"，那么发起调用这一步本身通常就应该很快返回（否则"发起"这个动作自己就变成了阻塞的），所以真正意义上的异步机制几乎总是和非阻塞的调用方式搭配出现，"异步阻塞"更多是为了让 2×2 的分类逻辑完整而列出的一格，实际系统设计里很少刻意去构造这种组合。

**常见追问 / 面试陷阱**

> 追问"`select`/`poll` 这种 IO 多路复用算同步还是异步"：算同步。调用方虽然可以一次监控多个描述符，避免了对每个描述符单独轮询，但 `select`/`poll` 本身仍然是调用方主动发起的、需要等待返回（哪些描述符就绪了）的调用，返回之后调用方还要再自己调用 `read()`/`recv()` 完成真正的数据拷贝——从"调用方需要主动参与等待和后续处理"这个角度看，`select`/`poll` 属于同步范畴的一种优化手段，而不是异步。这也是 Stevens 在《UNIX Network Programming》里的经典分类依据：判断同步还是异步，要看**真正完成数据搬运的那个动作**（读到用户缓冲区这一步）是否需要调用方自己参与、自己等它完成——按这个严格定义，阻塞 IO、非阻塞轮询 IO、以及 `select`/`poll`/`epoll` 这类 IO 多路复用全部属于同步 IO，因为数据就绪之后"把数据拷贝进用户缓冲区"这一步依然是调用方在阻塞状态下完成的；只有真正的异步 IO（比如 POSIX AIO，或者 Windows 的 IOCP，操作系统连数据拷贝这一步都替调用方做完了才通知）才算异步。本节的 2×2 象限是帮助建立"阻塞/非阻塞"与"同步/异步"这两个维度相互独立这一直觉的简化教学模型，具体到五大 IO 模型的严格分类，会在网络编程那一讲结合 socket 场景详细展开。
